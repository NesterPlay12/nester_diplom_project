# WildMarket

Онлайн-площадка с каталогом товаров, продавцами, заказами и административной панелью. Приложение работает на Python/Flask.

## Запуск после импорта в Replit

- Основной процесс: `artifacts/wildmarket: web`. Он запускает `flask-app/start.sh`
  с `APP_ENV=development`; порт передаётся через `PORT`. Отдельный старый процесс
  `WildMarket (Flask)` не нужен.
- Python-зависимости перечислены в `pyproject.toml` и `uv.lock`;
  Node-зависимости вспомогательных компонентов — в `pnpm-lock.yaml`.
- Для разработки используются управляемый PostgreSQL Replit,
  `FLASK_DATABASE_SOURCE=replit`, схема `FLASK_DATABASE_SCHEMA=wildmarket`
  и секрет `SESSION_SECRET`. Подготовка пустой схемы:
  `APP_ENV=development python flask-app/manage.py init-schema`.
- После импорта 22 октября 2026 года схема создана, но прежние данные
  **не восстановлены**. Указанный в `migration-manifest.json` снимок отсутствует
  в хранилище этого проекта. `wildmarket.zip` содержит только код, а
  `DIPLOM/instance/site.db` из приложенного RAR содержит три пустые таблицы
  старой версии. Не запускать `seed.py` вместо восстановления данных.
- Для завершения переноса нужен исходный дамп или доступ к прежней резервной
  копии. Настройка нового App Storage не переносит объекты старого проекта.
  Упоминания проверенного снимка ниже описывают предыдущую среду, а не наличие
  этой копии после импорта. Полное восстановление требует отдельной сверки
  таблиц, связей и файлов изображений.

Владелец использует сайт как production: не оставлять после проверок тестовые
категории, товары и заказы в публичном каталоге. Проверки с созданием записей
предпочтительно проводить в разработке; явно согласованные демо-ПВЗ и помеченные
демо-отзывы — отдельные функции, а не разрешение оставлять тестовые данные.

Владелец отдельно разрешил создать на опубликованном wildmarket.su четыре
презентационных аккаунта с ролями user, seller, admin и moderator. Это отдельные
аккаунты со случайными паролями, не восстановление старых общеизвестных демо-доступов.
Не отключать их автоматически как остатки технических проверок; основной
аккаунт владельца не менять. Пароли в коде и документации не хранить.

На главной странице приоритет — каталог товаров на первом экране, а не большой
рекламный баннер. По требованию владельца баннер на телефонах должен быть примерно
втрое компактнее исходного, на ПК — примерно в полтора раза; при дальнейших
изменениях не возвращать крупные вертикальные отступы и мобильное описание.

В мобильном каталоге фотографии товаров должны иметь одинаковую квадратную
область и показывать исходную картинку целиком, без обрезки. Это требование
владельца: компактные карточки, но без потери содержимого; десктопные размеры
при мобильных корректировках не менять.

## Демонстрационный самовывоз и Google OAuth

В админке есть раздел «Демонстрационные ПВЗ» (`/admin/pickup-points/`), доступный
только роли admin: добавление, редактирование, отключение и повторное включение.
Карта отображается через Яндекс; адрес и координаты здания подбираются вместе
через OpenStreetMap/Nominatim по запросу администратора (не автодополнение).
Можно проверить их вручную. Не принимать нечёткое совпадение другого номера дома.
Изменения сохраняются в PostgreSQL; старые заказы не переписываются.
Исходные адреса остаются доступными до первого изменения, а отключение сохраняется
явно и не отменяется при перезапуске. Подсказки городов в checkout обновляются
по действующему каталогу. Новая таблица применяется к production штатно при
публикации; запуск приложения и сборка не меняют схему БД.

Демонстрационные отзывы согласованы владельцем при явной пометке каждого примера.
Они заполняют разницу между существующим счётчиком товара и настоящими отзывами
без записи вымышленных пользователей, покупок или отзывов в БД. Рейтинг товара
не пересчитывается. Показаны все записи из счётчика, по 20 на странице; есть
оценки без комментария. Новые товары с нулевым счётчиком не получают примеров.
Настоящие отзывы отображаются первыми и не перезаписываются.
При добавлении настоящей оценки сохраняются исходные количество и сумма оценок
(среднее × количество), к ним прибавляется новая оценка. При удалении вычитается
только удаляемая настоящая оценка. Счётчик не пересчитывается только по таблице
`reviews`: в ней нет импортированных агрегированных оценок. Среднее хранится без
округления, округляется только для показа; изменения выполняются вместе с отзывом
в одной транзакции с блокировкой товара.

По решению владельца самовывоз демонстрационный, не для настоящей доставки.
Точки используют настоящие пары адрес/координаты OpenStreetMap (ODbL); их
идентификаторы и город проверяются сервером. В адресе заказа сохраняется отметка
«ДЕМО — не для реальной доставки». Демонстрационный каталог не вызывает API
операторов и доступен для 15 городов из подсказок.

Регистрация по email на wildmarket.su проверена в браузере. Google возвращал
`redirect_uri_mismatch`: владелец разрешил callback
`https://wildmarket.su/auth/google/callback` в существующем OAuth-клиенте Google.
Переход с production-домена к форме входа Google проверен: ошибки
`redirect_uri_mismatch` больше нет. Завершение входа с личным Google-аккаунтом
автоматической проверкой не подтверждено. Кнопка и начало OAuth доступны по
требованию владельца. `GOOGLE_OAUTH_ENABLED`
по умолчанию включён; при смене домена новый callback необходимо разрешить в Google.
Ключи не заменять. Ошибку Google Console нельзя исправить сменой базы или домена
в шаблонах приложения.

## Запуск

- **Flask-приложение**: управляемый воркфлоу `artifacts/wildmarket: web` — Gunicorn; старый `WildMarket (Flask)` остановлен
- `cd flask-app && APP_ENV=development python manage.py create-admin` — создать реального администратора с интерактивным вводом пароля; известные демо-адреса запрещены
- `cd flask-app && APP_ENV=development python manage.py secure-demo-accounts --confirm` — отключить известные демо-аккаунты и необратимо заменить их пароли, не удаляя записи и связи; повторный запуск не меняет уже защищённые записи
- `cd flask-app && python seed.py --demo` — создать демонстрационные данные для локальной разработки
- `cd flask-app && python run.py` — запустить вручную
- `cd flask-app && python -m unittest discover -s tests -v` — запустить регрессионные тесты

## База данных

**Только PostgreSQL**, включая разработку. SQLite/MySQL в конфигурации приложения запрещены; SQLite используется лишь как формат аварийного снимка и в изолированных регрессионных тестах.

Владелец согласовал полный перенос **всех** существующих данных без исключений, затем удаление старой рабочей SQLite. Перенесены все 8 таблиц, включая 7 пользователей, 14 категорий, 13 товаров, 2 заказа, 2 позиции заказов и 2 позиции корзины. Идентификаторы, хэши паролей, даты, NULL и связи сохранены; последовательности PostgreSQL выставлены для новых записей.

Для отдельного внешнего PostgreSQL используется секрет `FLASK_DATABASE_URL` (наивысший приоритет). В текущем проекте владелец выбрал управляемый PostgreSQL Replit: явная настройка `FLASK_DATABASE_SOURCE=replit` разрешает приложению использовать текущую управляемую строку подключения `DATABASE_URL`, не изменяя её и не дублируя секрет. Без явной настройки подключение не выбирается автоматически.

`FLASK_DATABASE_SCHEMA=wildmarket` изолирует Flask от таблиц Node-сервиса. `search_path` не включает `public`. Node-сервис продолжает использовать прежнюю конфигурацию.

Управление схемой выполняется **только в development**:
- `APP_ENV=development python flask-app/manage.py init-schema` — идемпотентная подготовка/обновление схемы.
- `APP_ENV=development python flask-app/manage.py restore-development` — восстановить проверенный снимок из закрытого App Storage **только если PostgreSQL пуст**; существующие записи не перезаписываются. После полной сверки полей, в той же транзакции, известные демо-аккаунты отключаются и получают случайные невосстановимые пароли. Остальные поля и связи сохраняются. Если в снимке нет реального администратора, его нужно создать вручную перед production.
- После слияния `scripts/post-merge.sh` выполняет подготовку схемы, восстановление пустой базы и идемпотентное отключение демо-доступа (в том числе в уже существующей development-БД). Ни сборка deployment, ни Gunicorn не выполняют DDL. Схема управляемой production-БД применяется штатным Publish, только по отдельному решению владельца.

Резервная копия находится в **закрытом** App Storage по пути из migration-manifest.json. Она скачана обратно, проверена по SHA-256 и восстановлена в отдельную схему PostgreSQL со сверкой всех полей. Нельзя выставлять ей публичный ACL или добавлять её в Git. Локальные отчёты и временные копии исключены из Git/deployment через `generated-artifacts/`.


### Регулярные копии текущего PostgreSQL

Владелец согласовал: **ежедневно в 03:00 Europe/Moscow, хранить 30 дней; уведомления о сбое — email планировщика Replit**. Возможная потеря новых данных между копиями — до 24 часов. Это отдельный процесс, не таймер Flask/Gunicorn и не development-workflow: Autoscale может засыпать. Исходная SQLite-копия переноса бессрочно исключена из этой очистки.

Однократный запуск в разработке:
`APP_ENV=development bash scripts/backup-postgres.sh`.
Проверки без реальных записей:
`APP_ENV=development python -m unittest discover -s flask-app/tests -p 'test_postgres_backups.py' -v`.
Реальная проверка закрытого хранилища и восстановления с контролем неизменности исходных записей и удаления временной БД:
`APP_ENV=development python flask-app/tests/postgres_backup_smoke.py`.

`flask-app/app/services/postgres_backups.py`:
- `pg_dump --format=custom --schema=<текущая схема>` сохраняет всю фактическую схему, включая новые таблицы, столбцы, индексы, ограничения, представления и последовательности. Список таблиц старого переноса не используется. Данные и дамп читаются из одного экспортированного `REPEATABLE READ READ ONLY` снимка; параллельные резервирования сериализованы advisory-lock.
- Объект создаётся с условием «не перезаписывать» в `PRIVATE_OBJECT_DIR/postgresql-backups/v1/<APP_ENV>/<идентификатор источника>/<схема>/`. Среды и источники изолированы. Нет публичного ACL, подписанных ссылок или HTTP-маршрута скачивания. App Storage шифрует данные при хранении; передача идёт по HTTPS. Отдельный клиентский ключ шифрования не вводился.
- Каждая копия скачивается обратно, сверяется SHA-256 и восстанавливается через `pg_restore --exit-on-error` в **новую отдельную БД**, не в новую схему рабочей БД. Проверяются количество и хэши всех строк всех актуальных таблиц. Только после успешного восстановления выставляется закрытая отметка `restore_verified=true` в метаданных объекта.
- Проверочная БД со случайным именем `wm_backup_verify_<random>` создаётся и удаляется только этим запуском. По умолчанию используется тот же сервер; требуется право `CREATEDB`. Секрет `WILDMARKET_RESTORE_DATABASE_URL` позволяет выбрать другой сервер/служебную БД с правом `CREATEDB`. Существующие БД никогда не используются как цель восстановления. Не выдавать это право веб-роли без отдельного решения владельца; для production предпочтительна отдельная служебная роль/сервер.
- В production `WILDMARKET_RESTORE_DATABASE_URL` **обязателен**. До дампа/загрузки проверяется, что это PostgreSQL и что проверочное подключение использует другой сервер или другую роль; смена только имени БД не считается изоляцией. Это не заменяет проверку реальных прав роли и назначения сервера владельцем. Автоматической выдачи `CREATEDB` нет. В development сохранён прежний режим проверки на том же сервере.
- После успешной проверки удаляются регулярные копии старше 30 дней только в префиксе этого источника, включая просроченные незавершённые копии. Текущая копия сохраняется. При сбое до окончания проверки очистка не выполняется. Generation-precondition защищает от удаления заменённого объекта.
- Временные файлы создаются вне репозитория в каталоге `0700`, файлы имеют режим `0600` и удаляются по завершении/обрабатываемой ошибке. При принудительном завершении процесса временные файлы могут остаться до уничтожения контейнера. Дампы запрещены в Git и deployment; `.dump`/`.pgdump` дополнительно исключены. Содержимое строк, SQL и пароли не выводятся в логи. Ошибка любой стадии, включая очистку проверочной БД/старых объектов, даёт ненулевой код выхода для уведомления планировщика.

**Статус активации:** подготовлены команда и согласованная политика в `flask-app/migration-manifest.json`; проверен реальный development-цикл upload → download → отдельная БД → сверка 9 текущих таблиц → удаление проверочной БД. Рабочее production-расписание и доставка email в рамках ветки **не включены и не проверены**. Не считать development-проверку защитой новых production-данных. Не менять тип публикации существующего веб-сервиса на Scheduled.

**Последнее решение владельца:** «Пока не включать» ежедневное задание; готовность отдельного служебного доступа PostgreSQL — «Не знаю». Активация отложена до нового явного разрешения. Не включать расписание автоматически после слияния и не считать согласованную ранее политику разрешением на запуск. Проверка production-восстановления и фактического получения email остаётся невыполненной.

После слияния отдельному Scheduled job нужны:
1. Команда сборки `uv sync --frozen`, команда запуска `APP_ENV=production bash scripts/backup-postgres.sh`, рабочий каталог — корень проекта; Python-зависимости из lockfile, PostgreSQL CLI совместимой с сервером основной версии (сейчас 16).
2. Cron **`0 0 * * *`, зона `UTC`** — это ровно 03:00 МСК круглый год. Если интерфейс использует Europe/Moscow, вместо этого задать `0 3 * * *`; не смешивать два варианта.
3. Доступ именно к **production** PostgreSQL (`FLASK_DATABASE_URL` либо явно `FLASK_DATABASE_SOURCE=replit` с production `DATABASE_URL`), `FLASK_DATABASE_SCHEMA=wildmarket`, закрытому App Storage и служебной роли для создания проверочных БД. Настройки нового job не считать автоматически унаследованными от веб-сервиса. Не копировать значения секретов в файлы или сообщения.
4. Тайм-аут задания с запасом на дамп, скачивание и восстановление (начать с 60 минут; каждая CLI-операция ограничена 20 минутами); включённые email-уведомления о неуспехе владельцу.
5. Первый ручной запуск задания с результатом `status=ok, restore_verified=true`; отдельно безопасный сбой проверки конфигурации для подтверждения прихода email. До этих проверок расписание нельзя считать включённым. Публикация/активация не выполняется автоматически при слиянии.

Ограничения: копируется только схема WildMarket, не роли сервера и не файлы фотографий в App Storage. Внешние зависимости схемы/расширения должны существовать на проверочном сервере, иначе job явно завершается ошибкой. Аварийное восстановление в рабочую БД — отдельная ручная операция с согласованием; этот job никогда не перезаписывает её. Email о неуспешном запуске не обнаруживает полное отсутствие запусков: для этого подготовлен отдельный контроль ниже.

### Независимый контроль свежести резервных копий

Владелец согласовал **36 часов** и «**Предупреждать только 1 раз, не засоряй мне почту**», канал — email отдельного Scheduled job Replit. Проверка раз в час: `APP_ENV=production bash scripts/monitor-backups.sh`, cron `0 * * * *`, UTC. Порог строго больше 36 часов; с учётом часового интервала обнаружение займёт до 37 часов от снимка. Это отдельное задание, не часть `backup-postgres.sh`, не Flask-таймер и не публичный HTTP-маршрут.

`flask-app/app/services/backup_monitor.py` использует общий с резервированием `backup_scope`: среда, фактический источник и схема должны совпадать. Читаются только имена, `timeCreated` и метаданные закрытых объектов. Нет скачивания дампов, подписанных ссылок, содержимого БД или путей в логах. Учитываются только штатные `.dump` с `format=postgresql-custom-v1`, `restore_verified=true` и корректным `verified_at` с часовым поясом. Возраст считается от снимка, а не только от проверки восстановления: повторная проверка старого дампа не делает его свежим. Будущие/некорректные отметки игнорируются; ошибка любого листинга, включая следующие страницы, считается `storage_error`, а не здоровым результатом по неполному списку.

Состояния: `missing` (нет подходящей копии), `stale` (просрочка), `storage_error` (нельзя проверить хранилище), `ok`. Постоянная защита от повторов — таблица `backup_monitor_states` PostgreSQL, только хэш области, флаг инцидента, статус и время проверки. Она намеренно описана отдельными SQLAlchemy metadata, **не** в ORM сайта: необязательный монитор не должен блокировать запуск веб-сервиса проверкой готовности своей таблицы. В development её готовит явная команда `manage.py init-schema`; production-схема применяется отдельно штатным процессом публикации. Advisory-lock сериализует перекрывающиеся запуски. При первом нездоровом результате флаг фиксируется транзакцией, и команда **однократно** возвращает код 1 для email планировщика. Последующие ошибки, включая смену `missing` → `storage_error`, дают код 0 с явным нездоровым статусом в приватных логах. Свежая проверенная копия снимает флаг; восстановление отмечается `recovered=true`, но отдельное письмо не отправляется. Новый сбой после восстановления снова даёт одно уведомление. Не очищать флаг вручную при продолжающемся сбое и не менять namespace существующего job: это разрешит новое письмо.

**Честные ограничения:** это не подтверждение доставки email и не гарантия exactly-once. Команда ограничивает число *попыток* уведомления через код выхода, а доставкой управляет Replit. Сбой процесса после фиксации флага, но до возврата кода 1 может потерять письмо. Если недоступна сама БД состояния или неверна конфигурация, безопасный статус `monitor_unavailable` пишется в stderr с кодом 0 — намеренный приоритет требования «не засорять почту», **не здоровый результат**. Автоматического письма в этом случае нет. Отключение самого контролирующего расписания также требует внешнего контроля. Не обещать устранение этих ограничений без отдельного независимого канала.

**Активация пока не выполнена.** Нужны:
1. Обычная публикация изменения схемы с таблицей состояния; никаких DDL в старте сайта/монитора или сборке. В разработке: `APP_ENV=development python flask-app/manage.py init-schema`.
2. **Второй** Scheduled job (не менять Autoscale сайта и не заменять ежедневное резервирование). Build `uv sync --frozen`, run `APP_ENV=production bash scripts/monitor-backups.sh`, cron `0 * * * *`, UTC, рабочий каталог — корень. Тайм-аут 5 минут. `pg_dump`, `pg_restore` и роль `CREATEDB` монитору не нужны.
3. Production-подключение к PostgreSQL с доступом к таблице состояния и тому же закрытому App Storage; `FLASK_DATABASE_SCHEMA=wildmarket`, явный `APP_ENV=production`. Секреты задаются через Secrets, не через файлы. Проверить, что источник совпадает с ежедневным job: development-копии не закрывают production-просрочку.
4. Включить email о неуспехе **контролирующего** job владельцу. Первый ручной запуск обязан дать осмысленный `ok` либо однократный `missing/stale/storage_error` с кодом 1. `monitor_unavailable` с кодом 0 — провал настройки, не успешная приёмка.
5. Получение первого письма подтверждает владелец; повторный запуск при том же сбое не должен создавать новый неуспешный запуск. После настоящей свежей копии — `ok, recovered=true`, затем проверить, что инцидент закрыт. Не подделывать метаданные настоящих копий и не удалять их ради теста.
6. Если ежедневный job имеет собственные email о каждом неуспехе, они не используют эту защиту от повторов. После проверки доставки нового монитора согласовать в Publishing единый канал предупреждений, иначе возможны дополнительные письма от ежедневного job. До проверки нового канала не отключать старые уведомления.

Проверки без дампов/почты: `APP_ENV=development python -m unittest discover -s flask-app/tests -p 'test_backup_monitor.py' -v`. Дополнительно проверка транзакций и блокировок на development PostgreSQL: та же команда с `TEST_BACKUP_MONITOR_POSTGRES=1`; создаёт только случайную строку состояния и удаляет её в `finally`. Ни расписание, ни факт доставки email эти тесты не подтверждают.

### Запуск сайта при отложенной схеме управления ПВЗ

Управление демонстрационными ПВЗ — дополнительная функция, не условие доступности магазина. Если при запуске отсутствует/неполна только `demo_pickup_points`, сервер явно пишет предупреждение и отключает её редактирование: авторизованный администратор получает объяснение с HTTP 503, изменения не принимаются. Карта и демонстрационное оформление продолжают использовать исходный адресный каталог, без запроса к отсутствующей таблице и без автоматического создания/заполнения таблиц. После штатного применения схемы и перезапуска снова доступны сохранённые настройки ПВЗ. Отсутствие/устаревание обязательных таблиц товаров, пользователей и заказов по-прежнему останавливает запуск с указанием проблемной таблицы.

**Почему:** отложенное добавление административной функции не должно вызывать общий `healthcheck / returned status 500`. Это ограниченный режим совместимости, а не выполненная миграция production и не разрешение на DDL в старте/сборке. Не расширять исключение на обязательные таблицы и не скрывать ошибки соединения с БД. Проверки: `PYTHONPATH=flask-app APP_ENV=development python -m unittest discover -s flask-app/tests -p 'test_deployment_readiness.py' -v`.

### Общая карта адресов

Владелец запросил просмотр всех добавленных точек сразу, без обязательного выбора города. В режиме адресного каталога `/delivery/pvz?provider=demo` без `city` возвращает все включённые точки всех городов; явно переданный `city` по-прежнему фильтрует ответ. Для официального каталога оператора город остаётся обязательным. Отключённые администратором точки не возвращаются ни в одном режиме.

Карта загружает весь адресный каталог при открытии выбора ПВЗ; перемещение и поиск только меняют область просмотра, не убирая точки других городов. Город выбранной точки берётся из самой записи, а не из текущего положения карты. Кнопка «Обновить» получает актуальный каталог и сбрасывает устаревший выбор. Появление точек в новом городе не требует добавлять его в фиксированные подсказки.

Повторяющиеся надписи «Демонстрационный режим»/«Демо-пункты» в интерфейсе карты заменены нейтральными подписями. Перед картой остаётся одно ясное пояснение, что адреса не являются действующими ПВЗ и получение посылок пока недоступно. В сохранённых заказах сохраняется признак нереальной доставки; действующие отправления не имитируются. **Почему:** убрать лишний визуальный шум можно, но адрес, привязанный к зданию, сам по себе не подтверждает возможность реальной выдачи посылки.

Демонстрационные аккаунты отключены с сохранением связанных записей; их пароли заменены случайными и не подлежат восстановлению. Их повторная активация запрещена сервером в обычной админке, кнопка разблокировки заменена пояснением. Для владельца настроен отдельный активный администратор. Секрет `WILDMARKET_ADMIN_PASSWORD` использовался только при ручной настройке: приложение не читает его при запуске и не сбрасывает по нему пароль. Восстановление старого снимка не должно возвращать демонстрационный доступ; production-проверку активных демонстрационных аккаунтов нельзя отключать.

Production требует `SESSION_SECRET` и **блокируется при наличии активных известных демонстрационных аккаунтов или отсутствии активного реального администратора**. Владелец разрешил защитить сохранённые демо-аккаунты без удаления данных. Ограничение доступа действует и для ранее выданных сессионных/remember-cookie: загрузчик пользователя проверяет актуальный `is_active` при каждом запросе. Приложение не создаёт пользователей и демонстрационные товары при старте и не читает `WILDMARKET_ADMIN_PASSWORD`. Первый реальный администратор создаётся вручную командой `APP_ENV=development python manage.py create-admin`. Проверка production-режима не является разрешением на публикацию.

Проверка реального staging без изменения рабочей БД:
`cd flask-app && APP_ENV=development python tests/postgres_staging_smoke.py`
Она клонирует данные в изолированную PostgreSQL-схему, запускает Gunicorn с `APP_ENV=staging`, проверяет CSRF, secure cookie, регистрацию, повторный вход, заказ и уменьшение остатка, затем удаляет тестовую схему.

Проверка защиты аккаунтов и production-старта без публикации:
`cd flask-app && APP_ENV=development python tests/postgres_account_safety_smoke.py`.
Она восстанавливает старый закрытый снимок в изолированную схему, проверяет отключение демо-доступа и действующего администратора, отказ production при активном демо-аккаунте, успешный запуск Gunicorn после защиты и отказ старых session/remember-cookie. Рабочие данные сверяются до/после и не изменяются.

## Функционал

**Покупатели:**
- Регистрация, вход, профиль
- Каталог товаров с фильтрами и поиском
- Страницы товаров с отзывами
- Корзина, оформление заказа
- История заказов, отмена
- Избранное

**Продавцы** (`/seller`):
- Добавление и редактирование товаров
- Статистика продаж
- Товары отправляются на модерацию

**Администраторы/Модераторы** (`/admin`):
- Dashboard со статистикой
- Модерация товаров (одобрить / отклонить)
- Управление пользователями (роли, блокировка)
- Управление заказами (смена статусов)
- Управление категориями (CRUD)
- Управление отзывами

## Архитектурные решения

- Flask Blueprints — каждый раздел в отдельном модуле
- Flask-SQLAlchemy ORM — PostgreSQL, отдельная схема WildMarket
- Flask-Login — сессии и защита маршрутов через декораторы
- Jinja2 шаблоны — наследование от base.html, admin/dashboard.html
- Bootstrap 5 из CDN — без сборщика, максимальная простота

## Gotchas

- Не менять `DATABASE_URL` Node.js API. Flask: отдельный `FLASK_DATABASE_URL` либо явный `FLASK_DATABASE_SOURCE=replit`, обязательно с отдельной схемой.
- Демонстрационные данные создавать только вручную для локальной разработки
- Admin-панель доступна ролям `admin` и `moderator`; назначать роль администратора может только `admin`
- Seller-панель доступна для ролей `seller` и `admin`
- Самовывоз работает в явно обозначенном демо-режиме с привязанными парами адрес/координаты. Для настоящей доставки допустимы только официальные каталоги операторов; включать её только по новому запросу владельца.
